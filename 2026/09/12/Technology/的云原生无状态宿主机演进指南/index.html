从不可变系统到 GitOps：基于 NixOS + k3s 的云原生无状态宿主机演进指南

在传统的 Linux 运维中，宿主机往往会随着时间推移积累大量的临时工具、历史包依赖以及不可逆的手动配置修改，即所谓的“配置漂移（Configuration Drift）”。本文总结了一种将不可变基础设施（Immutable Infrastructure）理念与轻量容器编排（k3s）结合的架构探索：让宿主机在重启时完全抹除状态，而所有的业务数据安全收敛于独立的数据目录。

一、 认知澄清：NixOS 是不可变系统吗？

严格来说，NixOS 并不属于传统意义上的不可变操作系统（如 Fedora Silverblue、Talos Linux）。

  • 传统不可变系统：核心系统目录物理只读（Squashfs / OSTree 镜像挂载），更新时下载整套新镜像并在重启时切换，应用强依赖容器（Flatpak / Docker）。

  • NixOS：没有任何上游发行版（完全从零独立构建），其本质是纯函数式、声明式的包与系统配置引擎。所有包存放在只读的 /nix/store 中，根系统由符号链接构成。修改配置后原子性切换软链接，天然支持配置版本溯源与秒级回滚。

通过将根目录（/）挂载为内存盘（tmpfs）并配合 impermanence 模块，NixOS 可以轻松实现比传统只读镜像更灵活的“无状态/不可变”形态——即社区著名的 Erase Your Darlings 架构。

二、 核心架构设计：状态与系统的物理隔离

为了实现“宿主机不可变，业务常驻”，必须打破应用与系统的强绑定，将状态彻底剥离至独立持久化盘（/data）：

关键路径重定向映射

k3s 默认会向 /var/lib/rancher/k3s 写入大量状态。若不干预，tmpfs 根目录会在关机后丢失这些数据。因此需进行全面重定向：

默认路径 规划路径 作用
/var/lib/rancher/k3s /data/k3s/data 集群元数据与状态库
/var/lib/containerd /data/k3s/data/agent/containerd 本地镜像与容器层
业务持久卷 /data/k3s/volumes 业务 Pod 的持久化存储

三、 技术路线横向对比

方案 机制与心智模型 持久维护方式 灾难恢复与一致性
NixOS (tmpfs + impermanence) 基础设施即代码 (IaC)





系统是配置的编译产物，重启自动重新生成


 声明式编辑配置，nixos-rebuild switch 毫秒级热切换 依靠 Git 配置文件，任何新机器均可 100% 重现完全一致的环境
Ubuntu (Overlayroot) “网吧还原卡”





传统系统层覆上一层内存联合挂载（OverlayFS）


 过程式进入 overlayroot-chroot 手动执行 apt update 底层镜像易黑盒化，长期维护依旧容易产生配置漂移
Talos Linux 全黑盒容器底座





无 Shell、无 SSH，纯 gRPC API 驱动


 通过 YAML 配置与 talosctl 管理，高度收敛 专为 K8s 设计，生产级免运维，但失去传统排查习惯

五、 构建产物与 GitOps 交付机制

许多初学者容易产生误解，认为操作系统 GitOps 需要像云厂商一样反复编译 ISO 或构建整机磁盘镜像。但在 NixOS 中：

  • 编译产物不是 ISO：而是存储在 /nix/store 中的一个闭包符号链接集合（System Closure）。

  • CI 验证能力：

  • nix flake check：静态语法与类型推导验证。

  • nix build ... --dry-run：零成本校验依赖构建合法性。

  • nixos-rebuild build-vm：在本地或 GitHub Actions 里一键秒起临时 QEMU 虚拟机，无实机验证启动与服务状态。

  • 交付流程：PR 合并后，借助 deploy-rs 或 colmena，CI 仅将数 KB 到数十 MB 的差异闭包通过 SSH 同步到目标机并原子性切换 /run/current-system 软链接。热更新无需重启，遇到异常自动超时回滚。

六、 渐进式实施计划

为了避免在生产环境因步子迈得太大而卡在硬件兼容或网络断连上，建议采取四步渐进落地：

  1. 第一阶段：标准安装与心智磨合

  • 使用常规 ext4 磁盘分区安装 NixOS，不启用 tmpfs。

  • 熟悉 configuration.nix、nixos-rebuild switch，体验从 GRUB 菜单倒退 Generation 秒级回滚。

  1. 第二阶段：服务与数据剥离

  • 挂载 /data 物理分区，配置 k3s 将 dataDir 导向 /data/k3s/data。

  • 部署带 PVC 的 Pod，验证容器存储和状态均成功落地在 /data。

  1. 第三阶段：无状态化改造（Erase Your Darlings）

  • 引入 impermanence，将 / 改挂载为 tmpfs，绑定 /nix 到 /data/nix。

  • 重启进行破坏性验证：确认宿主机临时文件消失，但 SSH 凭据与 k3s 集群完好常驻。

  1. 第四阶段：代码化纳管与自动部署
  • 将配置转为 flake.nix，固化依赖版本并纳入 Git 私有仓库，接入 deploy-rs 实现推代码即部署。
