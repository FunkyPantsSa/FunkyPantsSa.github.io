一、问题背景

最近在一台 Arch Linux 机器上部署 RustDesk，发现无法正常使用远程桌面功能。

RustDesk 提示：

这类问题通常与 Linux 桌面环境的 Portal、PipeWire、Wayland 会话及远程桌面权限有关。

与传统 X11 不同，Wayland 对屏幕捕获和远程输入有更严格的权限管理。应用程序不能简单地直接读取桌面画面，而需要通过桌面门户（XDG Desktop Portal）等组件申请相应能力。

因此，排查重点放在以下几个组件：

  • KDE Plasma：桌面环境。
  • XDG Desktop Portal：桌面门户接口。
  • KDE Portal Backend：KDE 桌面门户后端。
  • PipeWire：屏幕内容传输。
  • WirePlumber：PipeWire 会话管理。
  • RustDesk：远程桌面服务及客户端。

自动登录的安全问题

自动登录意味着任何能够接触机器的人，都可能在开机后直接进入该用户的桌面。

尤其需要注意：

  • 用户目录中的文件可能被访问。
  • 浏览器登录状态可能被利用。
  • 用户保存的 SSH 密钥可能面临风险。
  • 如果 RustDesk 配置了无人值守访问，远程访问风险也会增加。

因此，自动登录并不意味着应该让桌面一直保持解锁状态。

本次采用的方案是：

开机自动登录 → Plasma 初始化 → 检查远程服务 → 自动锁屏 → 通过 RustDesk 远程解锁。

安全注意事项

  1. 自动登录仍然绕过了开机时的本地用户密码验证，物理接触机器的人仍有机会访问桌面。
  2. 自动锁屏并不能代替磁盘加密。如果设备丢失，未加密磁盘上的数据仍可能被读取。
  3. RustDesk 无人值守访问应设置独立的强密码，并限制不必要的访问权限。
  4. 自动锁屏脚本检查的是本机服务状态，并不能证明外部网络已经可以连接 RustDesk。
  5. 首次重启测试时，建议保留 SSH 管理通道，不要关闭唯一的远程管理入口。

最后说明： 本次排查已经实际验证了 KDE 通过 D-Bus 锁屏，以及 RustDesk 连接锁屏界面后输入密码解锁的功能。自动锁屏脚本也已完成配置方案，但完整的开机自动登录、服务检查、延迟锁屏流程仍需要通过一次实际重启测试来确认。

总结

这次问题的关键不只是安装 RustDesk 或 PipeWire，而是确保 Wayland 桌面环境、Portal、PipeWire 和 RustDesk 都在正确的用户会话中运行。

对于需要无人值守运行的 Linux 桌面主机，可以考虑采用：

自动登录 + 服务就绪检查 + 自动锁屏 + RustDesk 远程解锁。

这样既能减少开机后人工干预，也能避免桌面长期处于未锁定状态。
